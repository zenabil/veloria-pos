**Audit ID:** `2026-11-11-full-forensic-audit`
**Skill loaded:** `veloria-db` — SKILL.md read in full (92 lines); references/invariants.md (38 L) and references/migrations.md (13 L) read in full.
**Method:** all 63 migration files read; schema extracted mechanically (`02_FILE_AUDIT/db-schema-extract.json`); `npm run verify:migrations` executed; `electron/database/sqlite.service.ts` read; 33 repository handler files inspected; migration lock verified against actual file contents.

## 1. Verdict

The database layer is the **strongest part of this project**. It is not "a SQLite file with a schema" — it is a deliberately engineered, layered integrity system: 63 forward-only migrations sealed by a sha256 lock, foreign keys enforced at the connection, 217 CHECK constraints and 77 triggers acting as a database-level wall beneath the application guards, WAL journaling with `synchronous = FULL`, and fail-closed snapshots before any destructive step. The substantive defects are **quantitative** (quantity columns declared `NUMERIC`, which in SQLite permits REAL / binary floating-point storage) and one **process** defect: the migration immutability lock can be regenerated by a script, correct only if discipline holds.

**Most important single fact:** the migration immutability guarantee is real and machine-enforced — editing any applied migration file now fails `npm run verify:migrations` with a hash mismatch. That is exactly the shape AGENTS.md rule 12 promises.

## 4. Findings

```text
ID: DB-01
TITLE: Stock quantity columns are declared NUMERIC, which in SQLite permits REAL (binary floating-point) storage
SEVERITY: P1
CONFIDENCE: VERIFIED
AFFECTED_SKILL: veloria-db (cross-ref veloria-stock)
AFFECTED_MODULE: database
FILE: database/migrations/0001_initial_schema.sql
LINE_RANGE: 88-89, 164, 187-188, 217-218, 244, 301, 315; 0018_fifo_cost_layers.sql:18-19,32; 0029_purchase_orders.sql:29-30; 0063_client_orders.sql:78,83
PROBLEM:
  Every quantity column in the schema is declared NUMERIC, not INTEGER. In SQLite,
  NUMERIC affinity converts a value to INTEGER when it is losslessly representable
  but stores it as REAL otherwise. The application layer enforces a thousandths
  scale (electron/ipc/handlers/fifo.ts:16 — const TH = 1000) and rounds on every
  write, so in practice quantities land as clean values — but the DATABASE cannot
  prevent a fractional value that is not a multiple of 1/1000, nor a value that is
  not exactly representable.
  The veloria-stock skill states: "Quantities use a documented base unit and fixed
  precision; do not accumulate binary floating-point quantities."
EVIDENCE:
  database/migrations/0001_initial_schema.sql:88
    quantity NUMERIC NOT NULL DEFAULT 0,
  database/migrations/0001_initial_schema.sql:164
    quantity NUMERIC NOT NULL,
  database/migrations/0018_fifo_cost_layers.sql:18-19
    original_quantity NUMERIC NOT NULL,
    remaining_quantity NUMERIC NOT NULL,
  database/migrations/0018_fifo_cost_layers.sql:32
    quantity NUMERIC NOT NULL,
  Mechanical extraction over all 63 migrations: 26 quantity columns, ALL NUMERIC.
  Contrast with money, which IS protected: 99 money-ish columns, all INTEGER
  (verify:migrations asserts "toutes les colonnes *_minor sont INTEGER").
ROOT_CAUSE:
  SQLite has no true DECIMAL type. NUMERIC was chosen as the closest available
  affinity. The thousandths discipline therefore lives entirely in application
  code (round3()) and in triggers, not in the column type.
IMPACT:
  A quantity that escapes the application rounding path (direct SQL, a future
  migration, an import path that writes a float) is stored as a REAL and can drift
  by binary representation error. Consequences: the FIFO invariant
  SUM(inventory_layers.remaining_quantity) = products.quantity can be off by
  ~1e-12 per row, and a physical reconciliation shows a spurious difference. The
  blast radius is small (the application rounds every write) but the database-level
  guarantee the stock skill asks for is absent, and any CHECK constraint on
  quantity must currently be written to tolerate REAL.
RECOMMENDED_FIX:
  Forward-only migration 0064 adding CHECK constraints asserting the sub-unit
  exactness and non-negativity on every quantity column, e.g.
    CHECK (ABS(quantity * 1000 - ROUND(quantity * 1000)) < 1e-9 AND quantity >= 0)
  This converts an implicit contract into an explicit one WITHOUT a table rebuild
  (a rebuild would be a risky data migration on a live retail database). If the
  team prefers an integer scale, a separate forward migration to milli-units
  (quantity_milli INTEGER) is the cleaner long-term option — but the CHECK
  approach is the correct first step.
REGRESSION_TEST:
  A database test that inserts a quantity of 0.0001 and asserts the CHECK rejects
  it; plus a test asserting SUM(layers) = product quantity for a mixed fractional
  dataset.
DEPENDENCIES:
  STK-02 (quantity precision), 09_CLOSING.md (stock valuation in zakat).
```

```text
ID: DB-02
TITLE: The migration immutability lock is regenerable by an npm script with no review gate
SEVERITY: P2
CONFIDENCE: VERIFIED
AFFECTED_SKILL: veloria-db
AFFECTED_MODULE: database
FILE: scripts/database/verify-migrations.mjs
LINE_RANGE: 62-72
PROBLEM:
  The immutability guarantee (AGENTS.md rule 12) is implemented as a sha256 lock
  file. `npm run verify:migrations:lock` regenerates that lock from whatever is
  currently on disk. The script documents the rule correctly, but there is no
  technical barrier to running it after editing an applied migration: CI would
  then be green and the drifted migration would be applied to new databases.
EVIDENCE:
  scripts/database/verify-migrations.mjs:64-71
    if (process.argv.includes("--write-lock")) {
      const lock = { schema: 1, algorithm: "sha256", note: "Immuable (AGENTS.md règle 12)…
        files: Object.fromEntries(files.map((f) => [f, fileChecksum.get(f)])) };
      fs.writeFileSync(LOCK_FILE, `${JSON.stringify(lock, null, 2)}\n`, "utf-8");
  package.json:60
    "verify:migrations:lock": "node scripts/database/verify-migrations.mjs --write-lock",
  The main-process runtime performs an INDEPENDENT checksum check of applied
  migrations against the live schema_migrations table, so an already-applied
  database WILL refuse to open with a drifted file — but a NEW database would
  silently apply the drifted file.
ROOT_CAUSE:
  The lock is a convention-plus-review control, not a cryptographically anchored
  one. Regeneration is deliberately available in the same commit that adds a
  migration, which is correct — but nothing distinguishes "lock updated for a NEW
  migration" from "lock updated to launder an EDITED old migration".
IMPACT:
  A drifted migration is detected for existing customer databases (the runtime
  guard fires) but not for fresh installs or for the verify script itself. The
  practical risk is a split-brain fleet: existing terminals refuse to open while
  new terminals install the drifted schema.
RECOMMENDED_FIX:
  Make `--write-lock` accept only ADDITIONS: read the existing lock, refuse to
  write if any pre-existing file's checksum changed (or if a file was removed),
  and require an explicit `--force-amend` (printing a justification) to override.
  This keeps the legitimate workflow intact and makes the laundering path
  deliberate.
REGRESSION_TEST:
  A test that copies a lock, mutates one already-listed migration, runs the
  writer, and asserts it exits non-zero.
DEPENDENCIES:
  None (self-contained).
```

## 5. What is genuinely solid

- **Migration immutability is machine-enforced.** `database/migrations.lock.json` stores a sha256 per migration; `verify:migrations` recomputes and fails on drift. This is exactly what AGENTS.md rule 12 promises.
- **Fail-closed pre-migration snapshot.** `sqlite.service.ts:145-151` throws "Sauvegarde pré-migration impossible : migration annulée." — the migration does not proceed with a warning.
- **FK enforcement at the connection.** `sqlite.service.ts:36-50` sets `foreign_keys = ON`, `journal_mode = WAL`, `synchronous = FULL`, `busy_timeout = 10000`, `wal_autocheckpoint = 1000`, `temp_store = MEMORY`, `trusted_schema = OFF`.
- **Business history is protected from cascade deletion.** `sale_items`, `sale_payments`, `stock_intake_items` all use ON DELETE RESTRICT.
- **Defensive invariants are explicit and iteratively hardened.** Migrations 0023 (`root_invariants`), 0026 (`defensive_invariants`), 0031 (`defensive_sale_item_discount`), 0040 (`explicit_restrict`) show a deliberate campaign to move invariants into the database, each verified by `verify:migrations` with a printed summary.
- **Idempotency is schema-backed.** `idempotency_keys` (0021) with a UNIQUE operation_id, extended with a status column (0061) — retries return the prior result rather than re-applying.
- **Closed-period protection is in the database.** Migration 0048 creates 15 fail-closed triggers; migration 0058 adds the business-day dimension.

## 6. Not verified / limits of this audit

- The live `Veloria POS DB.sqlite` was **never opened**. All schema statements derive from the migration SQL and from a disposable temp DB built by the verify script.
- Query plans were not captured via `EXPLAIN QUERY PLAN` for every statement; index adequacy was reasoned from the SQL plus the `verify:perf` timings.
- `electron/database/retention.ts` purge behaviour was not exercised against a database with expired rows.
- The 166 indexes were not each validated against a demonstrated query benefit (the skill asks for that); the audit confirms they exist, not that all are justified.
- Whether `schema_migrations` rows in real customer databases match the on-disk checksums was not verified (no live DB access).
